# Loop Mode

## Intent

Explore a new kind of deck — one optimised for playing looped sections of a track, so that a loop on one deck can play against a regular track on another.

This sits in a space between DAW clip-launching (Ableton, Bitwig) and live DJ beat-matching. DAW clips are convenient but pre-warped to perfection, missing the manual real-time skill that makes mixing fun. A deck loop, by contrast, would be a *played* object: imperfect at first, locked in by ear over time using small live adjustments. The same skill the DJ already uses to beat-match two decks, applied to one looping deck.

This is consistent with deck's philosophy — what the application "deliberately excludes" is *automatic* DAW-style looping, not *played* looping. The distinction is the human in the loop.

The concept is unproven, so the first step is a **minimal experiment** that tests the load-bearing hypothesis: *can a DJ actually lock a loop in by ear, using small live trim controls and a drift readout?* If yes, the fuller vision (tap-to-define gesture, drift-aware visualisation, infinite zoomed waveform, seam handling) is worth investing in. If no, the concept is dead and we've saved the effort.

The eventual interface would let the user define a loop by tapping out its bars, and tune it live as it plays — leaning on the same beat-matching instinct the rest of deck rewards, rather than on a precise pre-existing beat grid.


## Approach

Loop mode is a per-deck transport behaviour. While active, audio playback wraps from a loop end point back to a loop start point. Both the detail and overview waveform views remain available — the trio editing view is opt-in behind a toggle.

### Tap Entry, Looping playback, Phase nudge

`g` taps to enter loop (≥4 taps, rounded up to nearest power-of-2 bars). Audio wraps via the fade-on-seek path. `d` / `c` continue to nudge (no accumulator). Deck 3 only.

### Exit

`space+g` exits loop mode. (Single-press `g` is no longer overloaded as exit — it's purely the tap key now.) Conceptually a "loop mode toggle off"; pressed while not in loop mode it's a no-op.

### View integration

While loop mode is active on deck 3:

- **Detail waveform** stays a scrolling, playhead-tracking view — kept available for cross-deck sync. But it renders the loop content **infinitely wrapping**: any sample index `s` falling outside `[loop_start, loop_end)` is read from `loop_start + (s - loop_start).rem_euclid(loop_length)`. The user sees the looped audio repeating seamlessly, with the playhead moving steadily forward (no visible jump at the seam).
- **Overview waveform** is replaced by the **loop trio** while loop mode is active: left panel = ±50 ms around `loop_start`, middle = zoom-to-fit of the loop, right = ±50 ms around `loop_end`. The trio appears on loop entry and disappears on exit (`space+g`); no separate toggle. Overview returns to normal full-track view when loop mode exits.
- **Loop trio** in the overview area is height-constrained (2–3 rows of the existing OV_MIN/OV_MAX layout). It uses **single-dot braille precision** — see below.

The trio's role narrows from the previous build: it's the precision-edit view, brought into focus only when the user is trimming. The wrapping detail handles "is the seam audible?" with the existing waveform clarity.

### Single-dot braille precision

`render_braille` currently sets paired left+right dots per dot-row, so each waveform sample fills two horizontal dots. Single-dot precision computes peaks at sub-character resolution (2× the character column count) and renders each sub-column to **one** of the two dot positions (left or right) per dot-row. Each braille character then encodes two columns of waveform data side by side — doubling horizontal precision and giving the waveform a thinner, more precise visual line.

Used by the trio panels; the rest of the UI keeps the existing render.

### Endpoint trim — conditional override of jump keys

While `loop_state.active` on deck 3, the existing **jump 8 bars** and **jump 16 bars** keys are repurposed as loop-boundary trim — large bar jumps aren't useful for short loops. Direction follows the existing jump convention (number row = forward in time, letter row = backward in time):

| Key | Normal action        | In loop mode (deck 3)                                        |
|-----|----------------------|--------------------------------------------------------------|
| `4` | jump forward 8 bars  | `loop_start` += 1 ms (forward in time → loop shrinks from left) |
| `r` | jump backward 8 bars | `loop_start` −= 1 ms (backward → loop grows from left)       |
| `5` | jump forward 16 bars | `loop_end` += 1 ms (forward → loop grows from right)         |
| `t` | jump backward 16 bars| `loop_end` −= 1 ms (backward → loop shrinks from right)      |

Constraint: `loop_end - loop_start ≥ 1` sample. `loop_start ≥ 0`.

The previous `LoopEndLengthen` / `LoopEndShorten` / `LoopStartLengthen` / `LoopStartShorten` actions are removed; trim logic moves inline into the four jump action handlers, branching on loop state. `h` / `n` / `H` / `N` bindings are removed from `resources/config.toml`.

### Exit action

| Action       | Key       | Effect                                                  |
|--------------|-----------|---------------------------------------------------------|
| `loop_exit`  | `space+g` | Exit loop mode on deck 3. No-op when not in loop mode.  |

Still deferred (PoC). When the concept stabilises, this will materially affect Detail Waveform (looped wrap mode), Overview Waveform (toggle behaviour), plus a new Loop Trio node; Beat Grid will need the 5 ms offset catch-up.

## Feedback

**Status:** partially implemented

**Notes:**

- Build surprise (resolved): the first build wrapped the audio but not the display — `output_position` (which the display follows via drift snap) is only updated by `SeekHandle.seek_to()`, not by the loop-wrap path in `TrackingSource`. Fixed by passing `output_position` into `TrackingSource` and snapping it to `loop_start` when the wrap fires. (0.9.34)
- Second-iteration build (0.9.36) replaced detail with the three-panel trio while looping and added start trim on `H`/`N`. The three-panel concept works visually, but the UI integration is wrong: it monopolises the detail waveform, which is needed for cross-deck sync, and the detail can't be both "showing the looped audio" and "showing the trio". Also: stopgap key choices (`h`/`n`/`H`/`N`) need redesigning.
- **Second direction shift — needs re-plan.** Iteration desired:
  - **Integration:** the trio replaces the **overview** (behind a `space+g` toggle), not the detail. Detail stays as the playhead-tracking waveform but renders the looped content **infinitely wrapping** (samples beyond `loop_end` are drawn from `loop_start` onward, modulo loop length).
  - **Trio rendering:** single-dot braille precision instead of paired-dot, doubling horizontal resolution per character.
  - **Keys, redesigned:** `g` stays as loop tap / exit. Trim keys become **conditional overrides** of jump actions while loop mode is active on the deck — `4`/`r` override jump 8 bars (forward/backward) → loop end (lengthen / shorten); `5`/`t` override jump 16 bars (forward/backward) → loop start (shorten / lengthen). The current `h`/`n`/`H`/`N` bindings and dedicated `LoopEnd*` / `LoopStart*` actions are removed. `space+g` toggles the trio. Loop-shift (translate without resize) deferred.
- Tangential tweak made during testing (with user approval): offset-grid adjustment keys now step ±5ms instead of ±10ms, so the metronome can be aligned more finely while testing loops. Map's Beat Grid node still says "10ms steps" — stale catch-up edit pending. Cache/tap-derived offsets still snap to 10ms internally; only the manual keyboard step changed. (0.9.35)
- **Direction shift after early testing — needs re-plan.** The "lock-in by ear" mechanic (phase-nudge drift counter + ±1ms end-trim) didn't land. The user wants a visual-precision interface instead: a three-panel detail-waveform layout while looping — left panel high-zoom on loop start, middle panel zoom-to-fit loop with playhead, right panel high-zoom on loop end. Boundary markers in the side panels. Playhead visible across all three (sweeping rightward through the right panel, then reappearing at the left edge of the left panel post-wrap). Trim controls for **both** endpoints (currently only end). The planner should reconsider:
  - Whether the ear-based mechanic (drift counter, phase-nudge accumulator) is removed entirely, or demoted to a secondary indicator.
  - Layout of the three-panel view and the zoom window for the side panels (fixed vs user-controllable).
  - Start-trim actions, atomics, and keys (currently no start trim).
  - Render logic: a separate code path when `loop_state.active`, replacing the normal scrolling detail waveform.

**Documentation impact:**

- Map's Beat Grid node has a stale "10ms steps" mention from the tangential offset tweak — catch-up edit needed.
- The new three-panel design (when planned and built) will materially change Detail Waveform's role under loop mode; map will need attention then. Still deferred for the PoC.
